## 3. Growth evidence (≈ 6 minutes, 16:50 → 16:57)

* Live malloc bytes: 537.1 MB → 567.8 MB (+30.6 MB, ~1 min) → 600.2 MB (+32.5 MB, ~3.5 min later) → **plateaued at 598 MB** for 16:55–16:57 (6 samples 30 s apart, drift < 0.5 MB). Footprint is not monotonic (679 → 702 → 739 → 715 → 744 MB) because pages swap in/out; heap-live bytes are the reliable growth signal.
* Class deltas heap1 → heap3 (+63 MB): `Swift.StringStorage` **+90 642 objs / +42.0 MB**; `[DomainConnectionBindingSnapshot]` **+629 arrays / +11.0 MB** (39 → 250 → 668 arrays; `Dictionary<UUID,DomainRoutingOutcome>` 7 KB → 65 KB → 115 KB; `Dictionary<UUID,DomainConnectionBindingSnapshot>` 2 KB → 32 KB → 64 KB); `[String.Index]` +580/+2.6 MB; `[String]` +362; closure contexts +6 559; `MALLOC_LARGE` 1.6 → 6 → 13 MB (footprint rows).
* heap2 → … str3→str4 (~2 min) string growth was only +8 691 blocks / +0.5 MB (largest: 4 441 × 192 B, 2 097 × 160 B); and growth stopped during the idle 3-min window → growth is **activity-driven (bursty), not a steady-state leak while idle**.

### Growth finding A — MCP routing: connection registry + unbounded-by-count snapshot history ("quadratic" retention)
* `DomainRoutingCoordinator.finish()` stores a `DomainRoutingOutcome` for every routing operation, each embedding a full `DomainRoutingSnapshot` (all windows + **all connection bindings**), and keeps up to `maximumRoutingOperations = 4096` of them (`Sources/RepoPromptDomainRuntime/DomainRoutingCoordinator.swift:75-80,188,211-215,745-775`; `snapshot()` at :236). Memory ≈ ops × live-connections × binding size. Observed: 668 retained `[DomainConnectionBindingSnapshot]` arrays averaging 16.5 KB (11 MB) and rising linearly with MCP activity (39 → 250 → 668); cap is 4096 → worst case ≈ 4096 × (current avg 16.5 KB) ≈ **67 MB**, and more if the connection set keeps growing.
* The connection set itself grows: `UUID→DomainConnectionBindingSnapshot` dict storage 2 KB → 64 KB. Connections are registered from `MCPConnectionManager.swift:16067` (bind_context path before any window binding), `MCPServerViewModel+DomainRouting.swift:121,350`, but the only release path (`publishDomainRoutingRelease`, `MCPServerViewModel+DomainRouting.swift:143-175`, called from `MCPServerViewModel+TabContext.swift:543,4825`) is gated on `tabContextByConnectionID.removeValue(forKey:)` returning a context (:540, :4816). A connection registered by the transient/bind_context path that never acquired a tab context would never be unregistered. [INFERENCE — not verified which connections remain registered; verify by dumping `DomainRoutingCoordinator.snapshot().connections.count`.] No `unregisterConnection` call exists in `MCPConnectionManager.swift`.
* Also `registerConnection`/`unregisterConnection` take a fresh `UUID()` operationID each time, so the "idempotency" cache is useless while paying full snapshot cost per op.

### Growth finding B — StringStorage burst (+42 MB / 90 K strings in ≈ 4 min)
* Average new string ≈ 460 B ⇒ mix of many small strings and a few ~10–20 KB strings (str3→str4 delta shows 10 × 20 480 B, 6 × 12 288 B, 7 × 10 240 B …). Source not identified from the heap histogram alone; consistent with transcript/file-content string churn from MCP tool calls and Code-map manifest reload. [INFERENCE]

## 4. Cross-reference to caches/retained buffers (what bounds exist)
* `CodeMapRootManifestStore` decoded-manifest LRU: budget is **encoded file size** (`maximumDecodedManifestCacheByteCount = 64 MiB`, :83-124, accounting at :2551-2567) but the decoded in-memory representation is ~10–30× the encoded bytes (strings + arrays + Data per record, see consumer #1). Snapshot cache + `ManifestScanSummary` (small, counts only, :3286) — heap shows the cache dict is small (`ManifestCachedSnapshot` dict 262 KB) so the big retention is the **engine side** (`WorkspaceCodemapBindingEngine` `manifestRecords`/`automaticSelectionCandidateRecords`/`pendingManifestChanges`), per Git root, per pipeline identity.
* `WorkspaceSearchDecodedContentCache`, `HistorySessionScanner.IndexScanCache` exist (heap1) but are sub-MB dictionaries; not major.
* Transcript data (`AgentTranscriptRenderBlock`, `AgentChatItem`) ≈ 1.5 MB total — currently minor.

## 5. Recommendations (no code changed — read-only task)
1. Intern/share `CodeMapPipelineIdentity` (one instance per distinct identity; records hold a reference or compact ID) and store SHA-256 digests as fixed `(UInt64,UInt64,UInt64,UInt64)`/`InlineArray` instead of `Data`; use `StaticString`/enum for flag/limit names. Expected saving ≈ 100+ MB heap (≈ 17 strings + 2 arrays + 2.5 Data per record eliminated).
2. Make the decoded-manifest budget count decoded cost (or record count) and consider dropping `automaticSelectionCandidateRecords` when not needed; reconsider holding all records for all roots resident.
3. Trim `DomainRoutingOutcome.snapshot` (store revision/disposition only, or cap by bytes) and ensure every `registerConnection` has a matching unregister on disconnect, including bind_context-only connections.
4. To attribute the ~72 MB of large strings and the 1.5 MB ×5 buffers, restart under `MallocStackLogging=1` and `heap -addresses=Swift.StringStorage` / `malloc_history` (not done: would require relaunch, forbidden here).

## 6. Caveats
* `heap`/`footprint`/`vmmap` pause the process briefly (~10 s each); my runs likely induced some page-in (RSS growth 243 → 456 MB), but live-byte counts are unaffected.
* Peer analysis agents may have been issuing MCP calls to the same app during the window, which can drive finding A/B growth; the idle 3-minute window (16:55–16:57) shows zero growth.
* Heap type names for non-object blocks (e.g. `FileSystemService.fseventStreamRef (malloc)`) are guesses; treated as unattributed.
